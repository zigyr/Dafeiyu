# 变更管理（PCR）流程

> 适用项目：大肥鱼控制台（Dafeiyu Console）
> 维护：zigyr　最后更新：2026-10-31

## 1. 目的

让每一次需求都留下可追溯的闭环：

```text
需求 → 提炼/协商 → PCR → 实施 → 验证 → 交接文档 → 提交/推送
```

原则：

1. **先文档后代码**：PCR 经确认后才开始改代码。
2. **一次变更一个 PCR**：不把无关改动塞进同一次变更。
3. **可回滚**：每个 PCR 写明风险与回滚方式，提交保持原子性。
4. **可交接**：每次功能增删改都登记到根目录 `任务交接文档.md`。

## 2. 适用范围

| 需要 PCR | 可简化登记 |
| --- | --- |
| 新增 / 修改 / 删除功能 | 纯文案、注释、格式调整 |
| 界面与交互调整 | 依赖小版本升级且无行为变化 |
| 配置结构、数据结构变化 | 日志、临时脚本清理 |
| 部署 / 启动方式、依赖变化 | |

简化登记也必须写入 `任务交接文档.md` 的变更记录。

## 3. 角色

| 角色 | 职责 |
| --- | --- |
| 需求方 | 提出诉求、确认范围与验收标准 |
| 实施方 | 提炼需求、编写 PCR、实施与验证 |
| 评审 | 单人项目由需求方确认；涉及数据 / 安全变更需显式确认 |

## 4. 流程

### 步骤 0 · 需求提炼

把自然语言诉求整理为三要素：**问题、目标、验收**。信息不足时先提问，不猜测实现。

### 步骤 1 · 影响分析

从以下维度评估：模块 / 文件、配置、数据、接口、依赖、安全、兼容性、文档。

### 步骤 2 · 编写 PCR

复制 `docs/pcr/_模板.md`，命名为 `PCR-XXXX-简短标题.md`，填写完整后状态置为「草案」。

### 步骤 3 · 沟通确认

向需求方呈现：范围 / 非目标 / 方案取舍 / 验收标准 / 风险。
确认后状态改为「已批准」并记录确认时间。**未确认不进入实施。**

### 步骤 4 · 实施

按 PCR 的实施计划小步推进；提交信息引用 PCR 编号。

### 步骤 5 · 验证

至少覆盖：静态自检、关键路径手工验证、仓库状态检查。结果回填 PCR「验证记录」。

### 步骤 6 · 交接

在 `任务交接文档.md` 登记本次变更；PCR 状态改为「已完成」。

### 步骤 7 · 提交与推送

提交到 `main`；推送后核对远端与本地一致。

## 5. 编号与状态

- 编号：`PCR-0001` 起顺序递增，不复用。
- 状态机：

```text
草案 → 已批准 → 实施中 → 已完成
  └────────┴──────────→ 已取消 / 已回滚
```

## 8. 提交规范（Conventional Commits）

格式：

```text
<type>(<scope>): <中文摘要>

<变更说明，列点>

Refs: PCR-XXXX
```

| type | 用途 |
| --- | --- |
| feat | 新功能 |
| fix | 缺陷修复 |
| docs | 文档 |
| refactor | 不改变行为的重构 |
| chore | 构建、仓库、杂务 |
| test | 测试 |
| perf | 性能 |

scope 约定：`console` `core` `ui` `settings` `repo` `docs` `tools` `archive`。

## 9. 分支与版本

- 单人维护：直接提交 `main`，保证每个提交可运行。
- 高风险改动：`feat/<简述>` 分支，自测通过后合并。
- 发布：可选打 `vX.Y.Z` 标签，并在交接文档记录。

## 10. 与交接文档的关系

- `docs/pcr/` 回答「为什么改、改成什么、如何验收」。
- `任务交接文档.md` 回答「现在是什么状态、改过什么、怎么接手」。
- 每个 PCR 完成后必须在交接文档增加一条记录，二者通过 PCR 编号互相引用。
